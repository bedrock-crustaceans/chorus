# Development

Notes for working in this repository.

## Project

Chorus is Minecraft Bedrock Edition server software in Rust, built on [`bedrock-rs`](https://github.com/bedrock-crustaceans/bedrock-rs), with Bevy ECS (`bevy_app` / `bevy_ecs`, no full Bevy) as the tick and scheduling backbone.

- `bedrock-rs`, `bevy-raknet`, `bevy-nethernet` and `nbtx` are git dependencies on `branch = "main"`; `Cargo.lock` is committed. To develop against a local checkout add a temporary `[patch]` section and do not commit it.
- Vanilla worldgen data is the `bedrock_vanilla` crate (git dependency on `main`; its README describes every folder and its `tools/` folder holds the tools that regenerate the data). Data we write ourselves is in `crates/worldgen/resources` (README there). To work on the vanilla data locally use a `[patch]` section in an uncommitted `.cargo/config.toml`.
- Block state upgrade schemas and the item data are generated by `cargo run -p xtask`.

## Commands

```bash
cargo build [--release]
cargo run                                  # creates chorus.toml on first run
cargo fmt                                  # max_width = 200
cargo clippy --workspace --all-targets --features debug   # as CI does, warnings are errors (not --all-features)
cargo nextest run --workspace              # as CI does
cargo test --workspace --doc
cargo test --release -p chorus_worldgen -- --ignored output_checksum --nocapture   # worldgen output checksums

cargo run -p xtask -- block-upgrade-schemas        # network
cargo run -p xtask -- item-data [branch]           # network
cargo run -p xtask -- block-data [branch]          # network
```

## Workspace

The root package `chorus` (`src/`) is the server: network, commands, players, tick loop and the binary. Lower layers are in `crates/`: `core`, `block`, `item`, `entity`, `level` (world state, storage, generation framework), `structure_data`, `worldgen` (overworld, Nether and End generators), `network` and the transports `nethernet` (default) and `raknet` (optional).

Dependencies only point downwards. The root crate re-exports every crate as a module (`chorus::level`, ...); downstream users such as Pyrite depend on `chorus` alone. Shared dependency versions are in `[workspace.dependencies]`.
